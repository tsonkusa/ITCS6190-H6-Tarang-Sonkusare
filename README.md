# Hands-on L6: Music Streaming Analysis with the Spark Structured APIs

**ITCS 6190/8190 - Cloud Computing for Data Analysis - Fall 2026**

In Hands-on L5 you ran a word count on the Spark cluster and watched the job in the Spark
UI. This week you write the analysis yourself, with the DataFrame API from the L6 slides:

## The data

Two CSV files, generated by `datagen.py` from a seed that you choose (your student ID). The
files are yours: nobody else has the same numbers, and they can be regenerated exactly from
the seed.

`listening_logs.csv`, 1,000 rows, one per play:

| column         | type      | example               |
| -------------- | --------- | --------------------- |
| `user_id`      | string    | `user_59`             |
| `song_id`      | string    | `song_45`             |
| `timestamp`    | timestamp | `2026-03-24 15:00:47` |
| `duration_sec` | integer   | `109`                 |

`songs_metadata.csv`, 50 rows, one per song:

| column    | type   | example        |
| --------- | ------ | -------------- |
| `song_id` | string | `song_1`       |
| `title`   | string | `Title_song_1` |
| `artist`  | string | `Artist_4`     |
| `genre`   | string | `Pop`          |
| `mood`    | string | `Energetic`    |

Every user has a preferred genre that they play more often than the others, so the
favorite-genre and loyalty tasks have something to find.

## The tasks

All four are already laid out in `main.py` as functions that return a DataFrame. The
docstring of each function states the exact columns, ordering and tie-breaking rules; the
output of each task is written to `shared-folder/output/taskN/` as a single CSV file.

**Step 0. Load the data with an explicit schema.** `songs_schema` is given as a DDL string.
Write `logs_schema` as a `StructType` with four fields (`user_id`, `song_id`, `timestamp`,
`duration_sec`). Run the file before and after: with `logs_schema = None` every column is
read as a string, and `printSchema()` shows it.

**Task 1. Favorite genre per user.** Join the logs with the song metadata, count plays per
`(user_id, genre)`, and keep the genre with the most plays for each user (ties go to the
genre that comes first alphabetically). Output: `user_id, genre, play_count`, one row per
user, ordered by `user_id`. After this task the program prints the physical plan of the
result with `explain()`; you will need it for the report.

**Task 2. Average listening time per song.** For each song, the average of `duration_sec`
rounded to two decimals and the number of plays, with the song title attached. Output:
`song_id, title, avg_duration_sec, play_count`, longest average first.

**Task 3. Genre loyalty score.** For each user, the share of their plays that belong to their
favorite genre from task 1: `loyalty_score = play_count / total_plays`, rounded to three
decimals. Output the ten most loyal users: `user_id, genre, play_count, total_plays,
loyalty_score`, ordered by `loyalty_score` descending, then `total_plays` descending, then
`user_id`.

**Task 4. Night owls.** Users who listened between midnight and 5 AM (hour of the
timestamp from 0 to 4), with the number of such plays. Output: `user_id, night_plays`,
ordered by `night_plays` descending, then `user_id`.

Use only the DataFrame API (`pyspark.sql.functions`, `Window`). No RDD operations, no
`collect()` followed by Python loops, no pandas.

## Steps

### 1. Make your own copy of this repository

On the repository page, click the green **Use this template** button, then
**Create a new repository**. Name it `ITCS6190-H6-<your-name>` and set the visibility to
**Public**. Do not fork and do not clone this repository directly. Clone *your* repository
and work in it.

### 2. Generate your data

```bash
python3 datagen.py <your student ID>
```

Two files appear under `shared-folder/input/`. Open them and look at a few rows. Write your
seed in `REPORT.md`; the grader regenerates your data from it.

Without Python on your machine, start the cluster first (step 3) and run the generator in
the master container, which has Python 3:

```bash
docker cp datagen.py spark-master:/opt/spark/work-dir/shared/
docker exec spark-master python3 /opt/spark/work-dir/shared/datagen.py <your student ID> \
  /opt/spark/work-dir/shared/input
```

### 3. Start the cluster

```bash
docker compose up -d
```

Open <http://localhost:8080> and check that the master lists two workers in state ALIVE.

**In a GitHub Codespace**, start the cluster with the other compose file instead, as in
Hands-on L5:

```bash
docker compose -f docker-compose.codespaces.yml up -d
```

Inside a Codespace, traffic between containers on a Compose network can be dropped, so the
workers never register with the master and every job waits forever with `Initial job has not
accepted any resources`. That file puts the whole cluster on one network to avoid it.
Everything else is the same, except that `docker compose down` in step 7 also needs the
`-f docker-compose.codespaces.yml` flag.

### 4. Run `main.py` as it is

```bash
docker cp main.py spark-master:/opt/spark/work-dir/

docker exec -it spark-master /opt/spark/bin/spark-submit \
  --master spark://spark-master:7077 \
  /opt/spark/work-dir/main.py \
  /opt/spark/work-dir/shared/input \
  /opt/spark/work-dir/shared/output
```

The program loads the two files, prints the schema and the row counts, and reports each
task as "not implemented yet". Look at the schema: every column is a string.

### 5. Fill in the schema and the tasks, one at a time

Edit `main.py` on your machine. After each change, repeat the `docker cp` and the
`spark-submit` from step 4. A task whose function still returns `None` is skipped, so the
file always runs. Results are printed in the terminal (`show`) and written under
`shared-folder/output/`; outputs are overwritten on each run.

Working in the PySpark shell first is a good way to try an expression before putting it in
the file:

```bash
docker exec -it spark-master /opt/spark/bin/pyspark --master spark://spark-master:7077
```

### 6. Look at the plan and the Spark UI

Open <http://localhost:4040> while `main.py` runs; the application UI disappears when the
program ends, so start the run and switch to the browser (the program takes long enough), or
paste the tasks into the PySpark shell, where the UI stays up. In the **SQL / DataFrame** tab, find the query of task 1 and compare
its diagram with the `explain()` output printed in the terminal: find the two scans, the
join, the aggregation and the exchanges. Note how many jobs the whole program launched and
which line of your code triggered each of them.

### 7. Stop the cluster

```bash
docker compose down
```

## Troubleshooting

- **`no configuration file provided: not found`**: you are not in the folder that contains
  `docker-compose.yml`. `cd` into your repository first.
- **`python3: can't open file '/opt/spark/work-dir/main.py'`**: the `docker cp` in step 4 is
  missing, or you edited `main.py` and forgot to copy it again.
- **`Path does not exist: .../input/listening_logs.csv`**: run `datagen.py` first, and check
  that the files are under `shared-folder/input/` on your machine.
- **Every column is a string / `hour("timestamp")` fails**: `logs_schema` is still `None`.
  Complete step 0.
- **`[CAST_INVALID_INPUT]` or another ANSI error**: Spark 4 raises on invalid casts instead
  of returning NULL. Check the types in your schema and your expressions.
- **`AnalysisException: ... Reference 'song_id' is ambiguous`**: after a join on `song_id`
  with the `"song_id"` string form the column appears once; with `logs.song_id == songs.song_id`
  it appears twice. Use the string form, or select the columns you need before joining.
- **Results in a different order than specified**: `show()` on an unordered DataFrame prints
  rows in partition order. Add the `orderBy` from the task description.
- **`Permission denied` when writing the output (Linux)**: the containers run as user
  `spark` (uid 185). Run `chmod -R a+rwX shared-folder` and try again.
- **Job accepted but no progress, `Initial job has not accepted any resources`**: a PySpark
  shell is still open and holds the cores. Close it.
- **The master page shows no workers**: wait a few seconds and refresh; if they never appear,
  `docker compose logs spark-worker-1`.
